1. 학습내용

- DB를 연동한 리포지토리를 포함 서비스계층까지 자바코드로 작성


- Statement -> 쿼리문 작성 객체라고 생각하면 편할 듯 그리고 Statement 기본을 쓰는 건
SQL injection 공격에 취약해서 파라미터를 바인딩 해서 쓸 수 있는 PreparedStatement를 씀
- 커넥션 객체에서 prepareStatement(sql) 메서드를 활용해서 객체를 받고 활용
- statement의 종류로 미리 준비해놓는(일반 statement는 보안 및 효율 안좋음) 것, 파라미터를 바인딩 할 수 있음
즉, 저렇게 쿼리를 먼저 세팅하고 대기시켜놓은 다음 ?에 해당하는 벨류만 나중에 수정해서 올릴 수 있당
```
pstmt.setString(1, member.getMemberId()); // ?에다가 넣는 겁니다
            pstmt.setInt(2, member.getMoney());
            pstmt.executeUpdate(); // 준비해둔 설정을 반영해서 SQL 실행!
```

- 트랜잭션을 하려면 여러가지 조건이 필요하다
    1. 트랜잭션은 서비스 계층에서 시작해야 한다 -> 로직이 잘못되면 해당 비즈니스 로직을 롤백해야 하기 때문
    2. 어플리케이션에서 트랜잭션 적용 시 커넥션은 유지 필요 -> 그래야 같은 세션에서 사용 가능: 같은 세션에서 동작해야 트랜잭션 동작
  3. 트랜잭션 시작 시 커넥션 필요 -> 트랜잭션을 서비스로직에서 해야 하니 결국 서비스 계층에서 얻어야 함


- 같은 커넥션이 유지 되게 하는 방법 중 쉬운 방법은 파라미터로 커넥션을 받아 쓰는 것
- 그래서 리포지토리에서는 커넥션을 받는 로직이 없어야 하고 파라미터로 받게끔 사용
- 서비스에서는 커넥션을 받아 리포지토리에 다른 파라미터와 함께 같이 넘겨줘야 함


- 서비스 계층에서 비즈니스 로직에는 정상적으로 수행했을 때 커밋 예외가 터졌을 때 롤백을 해줘야 함
- 그리고 모든 자원들은 선언한 곳에서 반납을 해야 하는데 (Statement, Resultset, Connection 등)
커넥션은 서비스에서 호출했기 때문에 서비스에서 반납을 해줘야 한다. 
- 그리고 반납 할 때 트랜잭션을 구현했다면 con.setAutoCommit(false) 일 텐데 이걸 true(디폴트값)으로 돌려줘야 한다
다른 로직에서는 트랜잭션 없이 오토커밋 모드로 사용할 수 있기 때문!
